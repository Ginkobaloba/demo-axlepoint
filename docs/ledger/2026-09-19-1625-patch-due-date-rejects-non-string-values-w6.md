- **Change:** src/lib/wo-actions.ts, parseWorkOrderPatch's "due" case: removed the epoch-seconds fallback (asInt(body.due_date)) for a due_date that is not null and not a string. Any such value now returns { ok: false, error: "Invalid due date." }, which the PATCH route maps to 422. Added wo-actions.test.ts cases for true, [], 0, and {}, all expecting ok: false.
- **Why:** The old fallback called asInt(), which does Number(value): Number(true) === 1 and Number([]) === 0, both finite, so both were silently accepted as epoch-seconds timestamps and stored as a 1970 due date. POST /api/work-orders rejects the same true input (it never calls asInt for due_date). Grepped every caller of due_date in src/: only the date picker (work-order-controls.tsx) sends it, always a string or null, never a number, so removing the numeric path loses no legitimate use case. Note for the record: POST does not reject due_date: [] the same way (String([]) is "", so POST silently clears the date rather than rejecting it); this PR did not change POST, only PATCH, since POST's array handling was not the reported symptom.
- **State after:** demo-axlepoint's PATCH /api/work-orders/[id] now rejects true, [], 0, {}, and any other non-string, non-null due_date with 422, matching POST's stricter posture for string-coercible junk.
